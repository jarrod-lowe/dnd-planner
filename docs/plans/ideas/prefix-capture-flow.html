How a move opens: prefix capture

A move's opening amount is a pure function of the plan prefix — the facts at the row's position in the fold, derived synchronously from source-of-truth state. The 300 ms debounce exists only for displays: it can affect what you see, never what a choice opens at.

Fig 1 · the state landscape

Two planes that never touch

Store state splits into a synchronous plane that every mutation updates immediately, and a derived plane that trails it by up to 300 ms. Decisions read the first; displays read the second.

Fig 2 · the interactions

The tap is synchronous; the refresh is not

Every add and every OR INSTEAD swap runs the same exchange. The capture completes inside the tap, from source-of-truth inputs. The debounce fires later and refreshes displays only — it has no path back into a capture.

Fig 3 · the fold

A choice and its swap receive identical facts

The swap's default never sees the outgoing row's spend, because it is computed from the same prefix node the original choice opened against. Speed 30, one-row plan.

Worked example

What each interaction opens on

Character speed 30 ft. The rule: open on as much movement as is legal at the row's position.

interaction opens at why
add Walk, empty plan 30 ft prefix = the whole budget, as legal as it gets
Walk@15 planned → add Fly immediately 15 ft capture derives from plannedItems; a pending debounce refresh changes nothing
swap Walk@15 → Fly 30 ft prefix excludes the outgoing row's own spend
swap Walk@30 → Fly 30 ft same — the whole plan is the row being replaced
swap over-committed Walk@35 → Fly 30 ft same; over-commitment never reaches the prefix
swap row 1 after a Walk@35 row 0 ft earlier rows did over-commit → prefix negative → floored at 0

The last row is the clamp earning its keep: the prefix can legitimately be negative when earlier rows over-commit, because the planner projects over-commitment rather than preventing it — so captured numbers floor at zero.

Design decisions

Boundaries, deliberate

  • Freeze-at-add. An untouched row's amount doesn't re-derive when earlier rows change later — the value is frozen when the row lands; only the opening default is derived. Live re-derivation is a separate future idea.
  • The slider max is total / half_total. Dragging past what's left remains possible and shows the illegal-but-visible projection, per the engine's design.
  • addOfferToPlan flushes first. It reads the offer catalog — gate freshness at the append position — a genuinely cache-shaped need. The capture has no such need: it derives from source of truth directly.
  • The engine stays pure (plan.ts:78). The capture path is generic: every capture: true var — movement, steed moves, loadout, spell-prepare — flows through the same seam, and movement rules themselves carry no capture logic at all.
  • Prefix evaluation throws → no capture. The row opens on the rule's own authored defaults; a capture failure never blocks an add or swap.
